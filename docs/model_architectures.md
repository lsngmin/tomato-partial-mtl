# 🍅 Tomato Multi-Task: 모델 아키텍처 설명서

> 이 문서는 우리 논문에서 비교할 **5개 딥러닝 모델**의 구조와 설계 의도를 처음 보는 사람도 이해할 수 있도록 설명합니다.
> CV Baseline(HOG+SVM 등 전통 방법)은 제외합니다.

---

## 0. 먼저 알아야 할 것들

### 0.1 우리가 풀려는 문제

토마토 사진 1장이 주어졌을 때 두 가지 정보 중 하나를 알고 싶음:

```
사진 (224×224 RGB)
    ↓
┌─── 성숙도 (Maturity): Mature(빨강) 또는 Immature(초록)
└─── 품질 (Quality):    Fresh(신선) 또는 Rotten(부패)
```

**까다로운 점**: 우리 데이터셋은 **한 사진에 한 종류 라벨만** 있습니다.
- 어떤 사진은 성숙도 라벨만 있고 (품질 모름)
- 어떤 사진은 품질 라벨만 있고 (성숙도 모름)
- 같은 사진에 두 라벨이 동시에 있는 경우는 0건

이걸 학계에선 **"Partial Multi-Task Learning with Disjoint Labels"** 라고 부릅니다.
일반 MTL(같은 사진에 여러 라벨)과 다른 어려운 시나리오.

### 0.2 모든 모델의 공통 구성요소

```
┌───────────────────────────────────────────┐
│  Backbone (백본)                          │
│  - 사진을 고차원 특징 벡터로 변환            │
│  - 예: ResNet50, EfficientNet-B3, ViT-Base │
│  - ImageNet으로 미리 학습된 가중치 사용     │
└───────────────────────────────────────────┘
                  ↓
            Feature vector f
            (예: 2048차원 숫자 배열)
                  ↓
┌───────────────────────────────────────────┐
│  Head (헤드)                              │
│  - feature를 받아서 분류 결과 출력         │
│  - 보통 Linear(완전연결) + Softmax        │
└───────────────────────────────────────────┘
                  ↓
              Prediction
            (예: [0.9, 0.1] → Mature)
```

용어:
- **Backbone**: 사진을 의미 있는 숫자(feature)로 바꿔주는 큰 신경망. 우린 ImageNet pretrained 사용.
- **Head**: feature → 최종 답으로 매핑하는 작은 신경망. 보통 Linear layer 1~2개.
- **Pretrained**: 이미 다른 큰 데이터(ImageNet)로 학습된 가중치를 시작점으로 사용. 처음부터 학습하는 것보다 훨씬 빠르고 정확함.

## ② 모델 1: Single-task Maturity

가장 단순한 모델. **성숙도만** 분류하는 독립 모델.

### 구조

```
┌─────────────────────────────────────────┐
│   Maturity 이미지 (5,000장)              │
│   (Immature 또는 Mature 라벨만)         │
└─────────────────────────────────────────┘
                  │
                  ▼
        ┌──────────────────┐
        │   Backbone       │   ← ImageNet pretrained
        │   (ResNet50 등)  │
        └──────────────────┘
                  │
                  ▼            f ∈ ℝ^D   (예: D=2048)
        ┌──────────────────┐
        │  Maturity Head   │   ← Linear(D → 2)
        │  Linear + Softmax│
        └──────────────────┘
                  │
                  ▼
        ┌──────────────────┐
        │  Immature │ Mature │   ← 2-class 출력
        └──────────────────┘
```

### 학습 방식

```
손실 함수: Cross-Entropy (CE)
L = CE(예측, 정답)

데이터: Maturity 라벨이 있는 사진만 사용 (5,000장)
       → Quality 라벨이 있는 사진은 학습에 안 씀
```

### 왜 이 모델이 필요한가?
- **순수 비교 기준**: 다른 모델들이 정말 더 좋은지 비교하려면 "한 태스크만 단순하게 학습한" 베이스라인이 필요
- 학계의 표준 시작점

### 장점 ✅
1. **단순함** — 이해, 구현, 디버깅 쉬움
2. **태스크별 최적화** — Quality에 신경 안 써도 됨, Maturity에만 집중
3. **위험 없음** — 다른 태스크 때문에 성능이 떨어질 일이 없음 (negative transfer X)

### 단점 ❌
1. **데이터 절반만 사용** — Quality 사진(7,986장)은 학습에 못 씀 (낭비)
2. **모델 2개 필요** — Quality용도 따로 만들어야 함 → 메모리, 학습시간 2배
3. **태스크 간 지식 공유 불가** — "토마토 형태 인식" 같은 공통 지식도 따로 학습

## ③ 모델 2: Single-task Quality

② 모델과 구조 동일, 데이터와 헤드만 다름. **품질만** 분류.

### 구조

```
┌─────────────────────────────────────────┐
│   Quality 이미지 (7,986장)              │
│   (Fresh 또는 Rotten 라벨만)            │
└─────────────────────────────────────────┘
                  │
                  ▼
        ┌──────────────────┐
        │   Backbone       │   ← ②와 동일 구조 (가중치는 독립)
        └──────────────────┘
                  │
                  ▼
        ┌──────────────────┐
        │  Quality Head    │   ← Linear(D → 2)
        └──────────────────┘
                  │
                  ▼
        ┌──────────────────┐
        │  Fresh │ Rotten  │
        └──────────────────┘
```

### 장단점

②와 동일. **단**, 우리 EDA에서 발견한 사실:
- Quality 분류는 **색이 거의 동일** (R/G/B 채널 차이 3 이하) → 색만으로는 분류 안 됨
- **표면 텍스처** (부패, 곰팡이, 변색)를 봐야 함 → ②보다 본질적으로 어려운 태스크

→ Quality 모델은 더 깊은 특징 학습이 필요. 단순 backbone만으로 잘 안 풀릴 수 있음.

## ④ 모델 3: Joint Single-head (4-class)

두 태스크를 합쳐서 **하나의 4-클래스 분류 문제**로 푸는 방법.

### 구조

```
┌─────────────────────────────────────────┐
│   모든 이미지 (12,986장)                 │
│   원본 라벨: Immature/Mature/Fresh/Rotten│
│   → 4-class 문제로 변환                  │
└─────────────────────────────────────────┘
                  │
                  ▼
        ┌──────────────────┐
        │   Backbone       │   ← 공유 (하나만)
        └──────────────────┘
                  │
                  ▼
        ┌──────────────────────────────┐
        │      Single Head             │   ← Linear(D → 4)
        │   (4-class classifier)       │
        └──────────────────────────────┘
                  │
                  ▼
   ┌─────────┬──────────┬───────┬────────┐
   │Immature │ Mature   │ Fresh │ Rotten │
   └─────────┴──────────┴───────┴────────┘
```

### 학습 방식

```
손실 함수: CE (4-class)
한 사진에 한 라벨 (원래 한 라벨만 있으니까)
```

### 왜 이 모델을 비교군에 넣나?
- "굳이 멀티헤드 만들 필요 있나? 그냥 4-class로 풀면 되는 거 아냐?" 라는 의심에 대한 답
- 만약 이 모델이 멀티헤드만큼 잘 풀리면 → 멀티헤드의 의미가 없음
- 보통 멀티헤드보다 성능이 떨어지지만, 결과로 확인 필요

### 장점 ✅
1. **구조가 매우 단순** — 헤드 1개만 있으면 됨
2. **데이터 100% 사용** — 모든 사진 학습에 활용
3. **구현 가장 쉬움**

### 단점 ❌
1. **태스크 축이 뭉개짐**: 성숙도 ≠ 품질인데 4개 클래스가 같은 차원에 섞여 분류됨
   - "Mature이면서 동시에 Fresh인 것"은 표현 불가능 (단일 클래스 선택만 됨)
2. **추론 시 두 정보 동시 출력 불가** — Mature을 예측하면 Fresh/Rotten 정보는 못 얻음
3. **실용성 떨어짐** — 실제 농가/유통에선 두 정보 다 알고 싶음

→ 보통 비교 baseline용으로만 쓰이고, 메인 모델로는 부적합.

## ⑤ 모델 4: Naive Multi-head

**전통적 멀티태스크 학습 방식**. 공유 백본 + 두 개의 독립 헤드.

### 구조

```
┌─────────────────────────────────────────┐
│   모든 이미지 (12,986장)                 │
│   라벨: 사진마다 한 태스크만 (마스킹)     │
└─────────────────────────────────────────┘
                  │
                  ▼
        ┌──────────────────┐
        │   Shared Backbone│   ← 두 태스크가 공유
        └──────────────────┘
                  │
                  ▼            f ∈ ℝ^D
                  │
          ┌───────┴────────┐
          ▼                ▼
  ┌──────────────┐  ┌──────────────┐
  │ Maturity Head│  │ Quality Head │   ← 각각 독립
  │ Linear(D→2)  │  │ Linear(D→2)  │
  └──────────────┘  └──────────────┘
          │                │
          ▼                ▼
   Immature/Mature   Fresh/Rotten
```

### 학습 방식 (★ 핵심: 마스킹 손실)

```
각 사진마다 라벨이 있는 태스크만 학습에 반영:

if 사진에 Maturity 라벨 있음:
    L = CE(예측_mat, 정답_mat)
    (Quality 헤드는 무시)

if 사진에 Quality 라벨 있음:
    L = CE(예측_qual, 정답_qual)
    (Maturity 헤드는 무시)
```

### 왜 이 모델이 표준 비교 대상인가?
- Multi-Task Learning(MTL)의 **가장 흔하고 기본적인 형태**
- 우리 새 모듈(CTDR)이 이걸 능가해야 contribution 인정됨
- "그냥 헤드 두 개 붙이는 걸로 충분하지 않냐?"는 의심을 해소해야 함

### 장점 ✅
1. **파라미터 공유** — Backbone 한 번만 학습, 메모리 효율 ↑
2. **공통 특징 학습** — "토마토 형태", "조명" 같은 두 태스크에 공통인 정보를 한 번에 학습
3. **데이터 100% 사용** — 모든 사진이 어딘가에 기여
4. **추론 효율** — 한 forward pass로 두 결과 동시에 얻음

### 단점 ❌ (★ CTDR이 풀려는 문제)

**Negative Transfer 위험**:
```
Backbone이 한 사진 학습 시 한 태스크에만 끌림
   ↓
배치 1: Maturity 사진 8장 → Backbone이 "색 특징" 강화
배치 2: Quality 사진 8장 → Backbone이 "텍스처 특징" 강화 (앞서 학습한 색 정보 일부 손실)
배치 3: Maturity 사진 8장 → 다시 "색 특징" 회복 시도 (다시 텍스처 정보 손실)
   ↓
공유 백본이 두 태스크 사이에서 진동 → 둘 다 어중간하게 학습
```

특히 우리처럼 **두 태스크가 직교** (색 vs 텍스처)일 때 이 문제가 심각.

**우리 EDA 결과가 정확히 그 증거**:
- Maturity 분류: 색 차이 큼 (RGB 11~12 단위)
- Quality 분류: 색 차이 거의 없음 (RGB 3 단위)
- → 백본이 색을 너무 강하게 학습하면 Quality 성능 떨어질 수 있음

## ⑥ 모델 5: CTDR (Ours) ⭐

**Cross-Task Disentangled Routing** — 우리가 제안하는 새 모듈.

### 동기

> "Naive 멀티헤드가 직교 태스크에서 negative transfer를 겪는다면,
> 백본 특징을 **태스크별로 자동으로 분리**하는 모듈을 두면 어떨까?"

### 구조 (전체)

```
┌─────────────────────────────────────────┐
│   모든 이미지 (12,986장)                 │
└─────────────────────────────────────────┘
                  │
                  ▼
        ┌──────────────────┐
        │ Shared Backbone  │   ← Naive 멀티헤드와 동일
        └──────────────────┘
                  │
                  ▼            f ∈ ℝ^D
                  │
        ┌─────────┴──────────┐
        │   CTDR Module      │   ⭐ 새 모듈 (Ours)
        │  (다음 절에서 상세) │
        └────────────────────┘
              │       │
              ▼       ▼
         z_mat     z_qual         ← 태스크별 정제된 feature
              │       │
              ▼       ▼
   ┌──────────────┐  ┌──────────────┐
   │ Maturity Head│  │ Quality Head │
   └──────────────┘  └──────────────┘
              │            │
              ▼            ▼
       Immature/Mature  Fresh/Rotten
```

### CTDR Module 내부 (★ 우리 contribution의 핵심)

```
입력: 백본 출력 f ∈ ℝ^D

  ┌───────────────────────────────────────────────┐
  │                                               │
  │   ┌── W_s ──► f_shared  (공유 특징)            │  ① 3개의 선형변환으로
  │   │                                           │     feature를 3갈래로 분리
  │   ├── W_m ──► f_mat     (Maturity 전용)        │
  │   │                                           │
  │   └── W_q ──► f_qual    (Quality 전용)         │
  │                                               │
  │   ┌── W_gm + σ ──► g_mat  ∈ [0,1]^D            │  ② 학습 가능한 "게이트"
  │   └── W_gq + σ ──► g_qual ∈ [0,1]^D            │     0~1 사이 값
  │                                               │     (얼마나 공유할지 결정)
  │                                               │
  │   z_mat  = g_mat ⊙ f_shared + (1−g_mat) ⊙ f_mat │  ③ 게이트로 가중 평균
  │   z_qual = g_qual⊙ f_shared + (1−g_qual)⊙ f_qual│
  │                                               │
  └───────────────────────────────────────────────┘

⊙ = element-wise 곱셈
σ = sigmoid (0~1 범위)
W_* = 학습 가능한 행렬
```

### 한 줄씩 풀어 설명

**① 3갈래 분리**
- `W_s`: "두 태스크 공통으로 쓸 만한 특징" 추출 (예: 토마토의 둥근 형태)
- `W_m`: "Maturity에만 유용한 특징" 추출 (예: 빨강/초록 색)
- `W_q`: "Quality에만 유용한 특징" 추출 (예: 표면 매끄러움/거칠음)

**② 학습 가능한 게이트**
- `g_mat`이 1에 가까우면 → "이번 입력에 대해 Maturity는 공유 feature 위주 사용"
- `g_mat`이 0에 가까우면 → "이번 입력에 대해 Maturity는 전용 feature 위주 사용"
- 모델이 **학습 중에 스스로** 어느 쪽이 좋은지 결정 (입력마다 다르게 가능)

**③ 게이트로 가중 평균**
- 두 feature(공유 + 전용)를 게이트 비율로 합침
- 결과 `z_mat`이 Maturity 헤드의 입력이 됨

### 학습 방식 (★ 3개 손실 합성)

```
L_total = L_cls + λ_orth · L_orth + λ_gate · L_gate

L_cls   = Masked CE             ← Naive 멀티헤드와 동일 (분류 손실)
L_orth  = | cos(f_mat, f_qual) |²   ← f_mat과 f_qual을 직교화 (★ 새로움)
L_gate  = −H(g_mat) − H(g_qual)     ← 게이트가 0 or 1로 분명히 갈리도록
```

### 각 손실의 의미

**L_orth (직교 손실)**
- `f_mat`과 `f_qual`이 cosine similarity가 0이 되도록 압박
- 즉 "Maturity 전용 특징과 Quality 전용 특징은 서로 겹치지 마라"
- → 두 태스크가 같은 차원을 두고 싸우는 negative transfer 방지

**L_gate (게이트 엔트로피 손실)**
- 게이트 값이 0.5 같은 어중간한 값이 되지 않도록 압박
- "공유 feature를 쓸지 / 전용 feature를 쓸지" 결정적으로 정함
- → 해석 가능성 ↑ (어떤 입력엔 공유, 어떤 입력엔 전용이 쓰이는지 명확)

### 왜 이 설계인가? (기존 방법 대비)

| 기존 방법 | 차별점 |
|---|---|
| **Cross-Stitch** (CVPR 2016) | task feature를 linear로만 결합. 명시적 분리 X |
| **MMoE** (KDD 2018) | 여러 expert 사용. 단순 분리지만 expert 수만큼 파라미터 증가 |
| **Sluice Networks** (AAAI 2017) | 전체 텐서 결합. 너무 자유로워 학습 어려움 |
| **CTDR (Ours)** | **2-branch 분기 + 게이트 + 직교 손실** + **disjoint label 전제** |

### 장점 ✅

1. **명시적 feature 분리**
   - 게이트 학습으로 어떤 정보가 공유되고 어떤 게 분리되는지 모델이 스스로 결정
   - 직교 손실로 충돌 방지

2. **Negative transfer 완화**
   - 한 태스크 학습이 다른 태스크의 특징을 깎지 않음

3. **Disjoint label에 친화적**
   - 한 사진이 한 태스크 라벨만 갖는 우리 상황에 최적화

4. **해석 가능성**
   - 게이트 값 시각화 → "어느 feature가 공유되었나" 확인 가능
   - 논문에 좋은 figure 만들 수 있음

5. **추론 효율**
   - Naive 멀티헤드처럼 한 forward로 두 결과 얻음 (배포 시 빠름)

### 단점 ❌

1. **파라미터 증가**
   - W_s, W_m, W_q, W_gm, W_gq 5개의 새 선형층 추가
   - 백본 대비 작은 비중이지만 그래도 증가
   - → Ablation에서 "파라미터 늘려도 Naive로 같은 효과 나는지" 확인 필요

2. **하이퍼파라미터 추가**
   - λ_orth, λ_gate 두 개 더 조정 필요
   - → Ablation A3에서 그리드 서치

3. **학습 시간 증가**
   - 새 모듈 forward/backward pass 추가
   - 손실 3개 계산 → 단일 손실 대비 약 10~20% 느림

4. **이론적 보장 없음**
   - 직교 손실이 항상 도움 된다는 보장 없음
   - 어떤 경우엔 너무 강한 제약으로 작용 가능
   - → 실험으로만 정당화 가능

5. **구현 복잡도**
   - Naive 멀티헤드 대비 코드 양 ~2배
   - 디버깅 더 어려움

## 우리 선택: CTDR을 메인으로 가는 이유

### 1. 학술적 contribution이 명확

JFE Q1 같은 상위 저널은 "단순 적용"으로는 안 통과합니다. **새 모듈 제안 + 정당화**가 필요한데, CTDR이 그 역할.

### 2. 우리 데이터셋 특성과 정확히 매칭

EDA에서 발견한 것:
- **Maturity = 색 기반** (정보가 RGB 채널에 강함)
- **Quality = 텍스처 기반** (정보가 표면 패턴에 강함)
- → **두 태스크가 직교한 정보를 요구**

이건 Naive 멀티헤드가 가장 못 푸는 케이스. **CTDR이 해결할 정확한 문제**.

### 3. 비교 실험이 깔끔하게 짜임

```
RQ1: Naive 멀티헤드는 정말 negative transfer를 겪는가?
     → ② vs ⑤ 비교

RQ2: CTDR이 그걸 해결하는가?
     → ⑤ vs ⑥ 비교

RQ3: CTDR의 각 component(게이트, 직교 손실)가 필요한가?
     → Ablation

RQ4: 게이트가 의미 있는 분리를 학습하는가?
     → 시각화 + 정량 분석
```

각 RQ가 명확한 실험으로 답이 됨 → 리뷰어 만족.

### 4. 위험 분산

만약 CTDR이 Naive보다 좋지 않더라도:
- "직교 태스크 MTL에서 어디까지 가능한지 한계 분석"으로 프레이밍 가능
- Ablation 결과만으로도 educational value
- → 그래도 SCIE Q2~Q3급 통과 가능
